# G4 — retire the guidance that went wrong, reversibly

## Goal

mini-ork's memory lifecycle is **write-and-expire**. `MO_TRAJECTORY_TTL_DAYS` and
`mini_ork/dispatch/retention.py` remove entries by **age**, and nothing in the system models a
directive becoming **wrong**. An obsolete memory does not fail loudly: it is retrieved, injected,
and quietly steers a decision in a direction that no longer holds. Keeping it is not neutral
retention, it is active harm that grows with the size of the memory.

arXiv 2608.18177 reframes the memory lifecycle around **obsolescence** rather than age or storage
limits: three operational states (active / dormant / retired), transitions between them, and a
**reactivation path** so temporary suppression is never confused with permanent erasure. The
paper's own warning is that it "reports no measurement, no dataset, and no error rate, so this is
a design proposal rather than an evaluated method" — and that detecting obsolescence needs a
signal for "this guidance is now wrong," which it leaves open.

mini-ork already has that signal, and this is what makes the cycle worth building. The retrieval
ledger (`semantic_memory_uses`) records a **win/loss per memory per run**, and
`semantic_memory` carries the denormalized `uses` / `wins` counters that `_utility(uses, wins)`
turns into a Laplace-smoothed win rate. A memory retrieved six times and never once followed by a
passing run is a **measured** obsolescence candidate, not a guess. This cycle builds the
retirement mechanism on top of that existing evidence.

Two properties are load-bearing and both are testable:

1. **Retirement is a move, not a delete.** It is a flag with a reason and a pointer to the
   evidence that made the entry obsolete — reversible by design, because a retirement rule will
   sometimes be wrong.
2. **Suppression happens at the read path, not by deletion.** The injection channel
   (`context_assembler.semantic_lessons_md`) re-`upsert`s every approved pattern on **every
   assembly**, keyed by `pattern_id`. If retirement were a DELETE, the very next injection would
   resurrect it. So the retired entry must stay in the table and be filtered out of retrieval —
   and a repeat `upsert` of the same key must not clear the flag.

**Retirement is policy-gated.** `candidates()` *reports*; it never auto-retires. The paper is
explicit that retirement goes "through explicit policy rather than letting a score decide alone,"
and the hysteresis thresholds are asymmetric on purpose so an entry does not oscillate between
states as evidence wavers.

Reference: arXiv 2608.18177 (reversible forgetting — retire stale knowledge instead of always
retaining it).

## Deliverable 1 — `mini_ork/memory/retirement.py` (new)

```python
def retire(memory_id: int, reason: str, evidence_ref: str = "",
           *, db_path: str | os.PathLike[str] | None = None) -> bool: ...
def reactivate(memory_id: int, *,
               db_path: str | os.PathLike[str] | None = None) -> bool: ...
def retirement_state(memory_id: int, *,
                     db_path: str | os.PathLike[str] | None = None) -> dict | None: ...
def candidates(scope: str, *, db_path=None,
               enter: float = RETIRE_ENTER_UTILITY,
               exit: float = RETIRE_EXIT_UTILITY,
               min_uses: int = RETIRE_MIN_USES) -> list[dict]: ...
```

Semantics:

- `retire` sets `retired_at = time.time()`, `retire_reason = reason`,
  `retire_evidence = evidence_ref`. Returns `True` iff a memory with that id exists (the state
  after the call is always "retired"); `False` when the id is unknown. **Re-retiring an
  already-retired memory is a no-op that preserves the original `retired_at` / reason /
  evidence** — retirement history is not rewritten by a second call. `reason` must be a
  non-empty string (raise `ValueError` otherwise): a retirement without a stated reason is the
  opaque delete this design exists to avoid.
- `reactivate` clears all three columns to their defaults (`0`, `''`, `''`). Returns `True` iff
  the id exists. Idempotent — reactivating an active memory returns `True` and changes nothing.
- `retirement_state` returns
  `{"memory_id", "retired": bool, "retired_at": float, "reason": str, "evidence": str}`, or
  `None` when the id does not exist.
- `candidates(scope, ...)` reads the rows in `scope` and returns, sorted by `utility`
  ascending:
  - every **active** row with `uses >= min_uses` **and** `utility < enter` →
    `{"memory_id", "text", "uses", "wins", "utility", "state": "active",
      "recommendation": "retire"}`
  - every **retired** row with `utility > exit` →
    the same shape with `"state": "retired"`, `"recommendation": "reactivate"`

  Both directions in one call — that is the hysteresis: a row must fall below `enter` to be
  recommended for retirement and climb above `exit` to be recommended back. Raise `ValueError`
  when `exit <= enter`, because the asymmetry is the whole mechanism and a non-asymmetric
  configuration oscillates.
- Module constants: `RETIRE_ENTER_UTILITY = 0.25`, `RETIRE_EXIT_UTILITY = 0.45`,
  `RETIRE_MIN_USES = 4`. No env knobs — the CLI passes them explicitly.
- `retirement.py` may import from `semantic` (`_resolve_db_path`, `_connect`, `_utility`).
  **`semantic.py` must not import `retirement` at module scope** — that is a cycle.

## Deliverable 2 — schema + read-path suppression in `semantic.py`

- `_ADDED_COLUMNS["semantic_memory"]` gains three entries:
  `("retired_at", "REAL NOT NULL DEFAULT 0")`, `("retire_reason", "TEXT NOT NULL DEFAULT ''")`,
  `("retire_evidence", "TEXT NOT NULL DEFAULT ''")`.
- The `semantic_memory` CREATE inside `_BOOTSTRAP_SQL` lists the same three columns, so a fresh
  DB has them directly and `_ensure_columns` is only the upgrade path for an older DB.
- Filter retired rows out of **retrieval**: add `AND retired_at = 0` to the scope predicate in
  `_search_in_scope` (~344), `search` (~659), `rank_with_prior` (~763) **and** its scope-wide
  `SUM(uses)` at ~768 (UCB1's `N` must count the same rows the ranking can return).
- **Do not** add the filter to the `upsert` key lookup (~578), to `add`'s DELETE branch (~494),
  or to `record_retrievals`' existence check (~859). Those must still see retired rows — a
  retired memory still has ledger rows to reconcile, and the key lookup must find the existing
  row rather than inserting a duplicate.
- `mini_ork/memory/__init__.py` re-exports the retirement surface (`retire`, `reactivate`,
  `retirement_state`, `candidates`, and the three constants) and adds them to `__all__`.

## Tests — `tests/unit/test_memory_retirement_py.py` (new)

Hermetic; a tmp `db_path` per test; no network, no lane, no model. Numbered:

1. `retire()` → `retirement_state()["retired"] is True` with the reason and evidence echoed;
   `reactivate()` → `retired is False` and all three columns back to defaults. **Reversibility.**
2. `retire()` and `reactivate()` on an unknown id both return `False`; `retirement_state()` on
   an unknown id returns `None`.
3. Re-retiring preserves the original `retired_at` / reason / evidence (call `retire` twice with
   different reasons; the first survives).
4. `retire(reason="")` raises `ValueError`.
5. **End-to-end reversibility through the real retrieval path**: `search()` returns the memory;
   `retire()` it; `search()` no longer returns it; `reactivate()`; `search()` returns it again.
6. `rank_with_prior()` also excludes a retired memory.
7. **The resurrection hazard**: upsert the same `key=` twice while retired — the second `upsert`
   must leave it retired, and `search()` must still exclude it.
8. `candidates()` hysteresis — an active row with `uses=6, wins=0` (utility ≈ 0.125) is
   recommended `"retire"`; an active row with `uses=6, wins=6` is not; a retired row with
   utility above `exit` is recommended `"reactivate"`; an active row with `uses` below
   `min_uses` is absent even when its utility is low.
9. `candidates()` raises `ValueError` when `exit <= enter`.
10. `_ensure_columns` adds the three retire columns to a hand-built DB whose `semantic_memory`
    table predates them (create the table without the columns, then call the bootstrap path,
    then assert `PRAGMA table_info` shows them).
11. `from mini_ork.cli.main import SUBCOMMAND_REGISTRY; assert "memory-lifecycle" in
    SUBCOMMAND_REGISTRY`.

Set `uses` / `wins` by direct SQL against the tmp DB (or via `record_retrievals` +
`record_outcome`) — either is fine; be explicit in the test so the number under assertion is
the number set.

## Self-application (the measurement, not a claim)

A heredoc that seeds a tmp DB with one memory carrying `uses=6, wins=0`, then drives the real
API:

```
candidates(scope) must contain that id with recommendation "retire"
retire(id, "lost every attribution") -> True
search(query, scope) must NOT return it
reactivate(id) -> True
search(query, scope) must return it
```

Print `RETIREMENT IS REVERSIBLE` and write `${MINI_ORK_RUN_DIR}/rsi-g4-retirement.json` with:

```json
{"retirement_implemented": true, "reason_required": true, "reversible": true,
 "suppressed_from_search": true, "resurrection_hazard_covered": true,
 "hysteresis_asymmetric": true, "candidates_detected": 1,
```

`utility_of_candidate` must be the actual `_utility(6, 0)` value computed at runtime — do not
hardcode it; the smoothed rate is `(0+1)/(6+2) = 0.125`.
