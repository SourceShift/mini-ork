# E4 edit-scope declaration and rollback targets

## Goal

A mutation request carries no declared scope, so an out-of-scope hunk can ride
along inside an accepted change. This is also why the known framework-edit failure
is dangerous: the recipe stashes the whole working tree, so an orphaned edit is
invisible until it resurfaces.

### Mechanisms (exact spec)

Add a `scope` field to the mutation request naming the recipe, prompt file, node,
and section the change is permitted to touch. Before `apply_mutation`
(`mini_ork/cli/apply.py:536`) lands anything, parse the produced patch and reject
the whole candidate when any hunk falls outside the declared scope, recording
which path violated.

Keep prior accepted harness snapshots in `mini_ork/workflow/store.py` beside the
`MO_APPLY_*` knobs, so the search has a starting point other than the last
acceptance and the previous version can be restored without a git operation.

Scope is enforced as an allowlist of editable paths per task class, not a
denylist. A file absent from the allowlist is not an edit target, which also
bounds the blast radius of a bad proposal.

### Tests

Extend `tests/unit/test_apply_mutation.py`. Assert: an out-of-scope hunk rejects
the whole candidate; an in-scope patch lands unchanged; a retained snapshot
restores byte-for-byte.

### Self-application measurement

Inject a candidate whose patch touches one file inside its declared scope and one
file outside it. Baseline: it lands (today's behavior). After: it is rejected.
Accepted iff the out-of-scope reject rate is 100% and the in-scope pass rate is
100%.

Evidence artifact: `${MINI_ORK_RUN_DIR}/scope-control.json` with
`{"out_of_scope_rejected": <int>, "out_of_scope_total": <int>, "in_scope_landed": <int>, "in_scope_total": <int>}`.

### Done When

- Out-of-scope rejection is total and the violating path is recorded.
- A prior snapshot restores exactly.
- The allowlist is a named artifact, not inline logic.
