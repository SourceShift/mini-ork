# E1 code-arm probe harness — measure a code improvement

## Goal

`mini_ork/learning/probe_scorer.py` can only score a directive: `_materialize_arm`
(line 214) copies `recipes/<task_class>` to a temp recipe and appends a directive
block to a prompt file. A change to gate arithmetic, lane routing, or a harness
module cannot be scored by it, which means "run the improvement and see whether it
was real" is currently impossible for every candidate in the top-20 except prompt
edits. Build a code arm that varies the framework tree, not the prompt text.

### Mechanisms (exact spec)

`probe_score_code(task_class, patch_path, *, base_ref="HEAD")` in
`mini_ork/learning/probe_scorer.py`. It reuses `_frozen_probes`, `_probe_fixture`,
`_materialize_target`, `_run_outcome`, `_run_cost`, the `MO_APPLY_PROBE_*` budget
knobs, and the existing `finally` cleanup verbatim. It differs only in how the two
arms are built: the baseline arm is `git worktree add --detach <tmp>/base
<base_ref>`; the candidate arm is the same worktree followed by `git -C
<tmp>/cand apply --check <patch_path>` and then `git apply <patch_path>`. A patch
that fails `--check` returns `None` — never a fabricated neutral score.

`_launch_run(recipe_name, kickoff, target_cwd=None, root=None)` sets
`MINI_ORK_ROOT=<root>`, `MINI_ORK_HOME=<root>/.mini-ork`, and
`MINI_ORK_DB=<root>/.mini-ork/state.db` in the subprocess environment when `root`
is given. `_run_outcome` and `_run_cost` gain a `db=` parameter, because reading a
score from the wrong arm's database is the exact failure this section exists to
prevent.

Both worktree copies get `recipes/<task_class>/probes/` removed before any run,
for the same reason `_materialize_arm` strips it: the probe set stays frozen to
the original tree and nothing can recursively re-probe.

`MO_APPLY_SCORER=code` selects `probe_score_code` in `evaluate_gate`
(`mini_ork/cli/apply.py:332`). Default stays `directive`. A `code` score whose `n`
is below `MO_APPLY_MIN_EXAMPLES` is treated as no score, so the gate quarantines
rather than promoting.

### Tests

New `tests/unit/test_probe_scorer_code_arm.py`. Build a throwaway git repo in
`tmp_path` with one committed file. Assert: the candidate arm's file carries the
patch and the baseline arm's does not; a patch that cannot apply returns `None`;
both worktrees are removed in the `finally` path; `_run_outcome` with an explicit
`db=` reads that database and not the ambient one. Monkeypatch `_launch_run` as
the existing probe tests do — never shell out to a real lane in a unit test.

### Self-application measurement

Baseline is the null calibration and nothing else: run `probe_score_code` with an
empty patch. The instrument is accepted iff the empty-patch delta is within
`MO_APPLY_REGRESSION_TOLERANCE` on at least `MO_APPLY_MIN_EXAMPLES` probes. An
instrument that reports a non-zero delta for a no-op is rejected and fixed before
any other epic uses it.

Evidence artifact: `${MINI_ORK_RUN_DIR}/code-arm-null-calibration.json` containing
`{"patch": "", "before": 0.0, "after": 0.0, "n": <int>, "delta": <float>}`.
